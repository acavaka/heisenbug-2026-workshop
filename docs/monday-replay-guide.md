# QAI в понедельник: повторение и первый рабочий кейс

Начните с файлового BUG-LAB-01, чтобы отделить настройку агента от настройки Kubernetes. Затем перенесите подход на один разрешённый кейс своего проекта. Ниже — маршрут для текущего учебного репозитория, а не готовое production-развёртывание.

[Все материалы](workshop-kit.md) · [Задание trace_to_logs](../workshop/exercises/trace_to_logs/README.md) · [MCP](../workshop/exercises/mcp_connection/README.md)

## 1. Сохраните результат воркшопа

Сохраните версию/commit проекта, правку `workshop/prompts/qai-data-investigator.md`, свою функцию `correlate` и description в `workshop/skills/trace_logs.py`, отчёты и транскрипты. Ключи, `.env` и kubeconfig в коммит не добавляйте. Для нового запуска выбирайте новый путь отчёта: старые ошибки нужны для сравнения.

Если используете чистый учебный выпуск, `correlate` может снова содержать TODO. Это ожидаемо: перенесите свою реализацию или повторите задание. Не копируйте весь модуль решения поверх рабочей версии. Примеры команд ниже выполняются из корня проекта.

## 2. Подготовьте Python и выбранную программу

На том же ноутбуке используйте существующее `workshop/.venv`. Для нового ноутбука сначала получите ту же версию проекта и подготовьте окружение по [prework](participant-prework-draft.md). Для файлового кейса Docker, Kind, kubectl и k8sgpt не требуются. Для live MCP k8sgpt они понадобятся отдельно; application MCP в replay читает файлы без Kubernetes.

Минимальная подготовка нового Python-окружения на macOS/Linux:

```bash
python3 -m venv workshop/.venv
workshop/.venv/bin/python -m pip install -r workshop/requirements.txt
workshop/.venv/bin/python -m pip check
source workshop/.venv/bin/activate
```

Windows PowerShell:

```powershell
py -3 -m venv workshop/.venv
workshop/.venv/Scripts/python.exe -m pip install -r workshop/requirements.txt
workshop/.venv/Scripts/python.exe -m pip check
workshop/.venv/Scripts/Activate.ps1
```

Если `py` отсутствует, используйте установленный Python согласно prework. Если активация запрещена, во всех командах ниже заменяйте `python` на полный путь `workshop/.venv/Scripts/python.exe` или `workshop/.venv/bin/python`. Используйте согласованную версию Python выпуска: текущий requirements задаёт нижние границы зависимостей и сам по себе не фиксирует воспроизводимое окружение на любой ОС.

Для редактора используйте его обычную авторизацию. Для стандартного API-маршрута Python нужны зависимости и рабочие `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `MODEL` в локальной конфигурации. При отсутствии `.env` создайте его из `workshop/.env.example`, сохраняя уже имеющиеся настройки; не используйте URL-заглушку как рабочий endpoint. Не показывайте содержимое файла агенту или в отчётах.

## 3. Повторите файловый кейс без модели

Откройте новый терминал, чтобы не унаследовать переменные live MCP. Активируйте venv. Эти команды читают локальные синтетические данные и не меняют стенд:

```bash
python workshop/exercises/trace_to_logs/run.py report
python workshop/exercises/trace_to_logs/run.py pods
python workshop/exercises/trace_to_logs/run.py check
python workshop/exercises/trace_to_logs/run.py prepare --case complete
```

Ожидаемый результат:

- `report` и `pods` читаются без Kubernetes и доступа к модели;
- после вашей реализации `check` возвращает `passed=true`, exit 0; на стартовом TODO FAIL ожидаем;
- `prepare` проверяет возможность корреляции; это ещё не подтверждение root cause.

Если `check` падает, откройте ошибку и исправьте функцию, не эталонные данные и не проверку. Не переходите к сравнению моделей, пока ошибка находится в инструменте.

## 4. Запустите модельного оркестратора или нативный редактор

### Python-харнесс

После своей реализации correlate выполните из корня:

```bash
python workshop/exercises/trace_to_logs/orchestrator_replay.py --case complete --output workshop/.local/monday-complete-01
```

Это API-маршрут. Если API не выбран, используйте поддерживаемый **только этим runner** транспорт
Codex по подписке: проверьте `codex login status`, добавьте `--provider codex` и выберите новый output.
Модель выбирает роли и досбор; Python исполняет инструменты и валидирует обычный application-ответ.
Сохраняются BUG-LAB-01.json, trace, role-reports.json и validation.json. Ошибки сохраняйте для сравнения.
`validation.json` проверяет контракт; поведенческий ключ остаётся у ведущего. Проверьте смысл ответа по источникам.

### Codex, Claude Code или Cursor

Подключите [application MCP](application-mcp.md) в режиме replay complete.
После правки correlate перезапустите сервер. Начните новый диалог с запросом из
[карточки 4](../workshop/exercises/trace_to_logs/README.md). Редактор сам вызывает qai_begin,
qai_observe и qai_validate; его подписка не требует API-ключа MCP-серверу.
Сохраните транскрипт и фактический ответ valid=true. Этот маршрут отличается от Python,
использующего Codex только как модельный транспорт.

### Проверьте результат сами

Покажите фактический вызов своей функции, ID и окно, код и связанные логи, исключённую чужую
ошибку, неизвестное влияние пропусков и принятие полного вердикта. Valid=true проверяет контракт
и происхождение цитат, но не заменяет оценку смысла. High не обязателен.

## 5. Проверьте границу отказа

Выберите no-ids с новым output в Python либо перезапустите application MCP с --case no-ids
и начните новое расследование. Ожидается запрос данных при неподтверждённой корреляции:
root_cause пуст, confidence low; код не используется для подтверждения причины.
В новом оркестраторе модель работает, runtime ограничивает дальнейшие действия.

`run.py prepare --case no-ids` проверяет gate офлайн. Это проверка корреляции, а не поведения модели.
Для других усложнений выберите missing-logs, incomplete-trace или invalid-trace из карточки.
Сохраните первый неудачный ответ; меняйте одну инструкцию за раз при одинаковых входах и модели.

## 6. Если хотите повторить live MCP

Это отдельный маршрут. Используйте [карточку 3](../workshop/exercises/mcp_connection/README.md), [описание MCP](k8sgpt-mcp.md) . Получите read-only профиль у ведущего. Подготовка выполняется владельцем локального учебного кластера до расследования. Не запускайте её против рабочего Kubernetes.

Локальный `mcp-live.json` должен ссылаться на бинарники и read-only kubeconfig именно вашего ноутбука. Проверяйте namespace `qai-training`, ограничения операций и настройки `exclusive`. Не копируйте абсолютные пути и credentials ведущего.

Подключение проверяется в три этапа: сервер объявил инструменты → агент прочитал Pod и события → вердикт принят и проверен человеком. `tools/list` или `mcp_check` подтверждают только первый этап. Для редактора нужен маршрут через gateway и `qai_observe`, чтобы регистрировать доказательства. После этого смотрите `qai_validate.valid`; Python проверяет вердикт в runtime. После упражнения закройте live-терминал.

## 7. Первый кейс на работе

Предлагаемый небольшой пилот — один кейс, один источник и один человек, который знает реальную причину. Время зависит от доступов; начните с локальных обезличенных/синтетических снимков в разрешённом контуре модели.

| Шаг | Что подготовить | Как понять, что получилось |
|---|---|---|
| Определить вопрос | Один баг и границы расследования | Понятно, что считать ответом |
| Собрать replay | Репорт, trace, логи, код, известные пробелы | Есть связь по ID/времени и проверяемая причина |
| Задать правила | Факты/выводы/гипотезы, ссылки, остановка при нехватке данных | Неподтверждённое не превращается в факт |
| Подключить инструмент | Одна функция или MCP-операция на чтение | Видны аргументы, исходный ответ и ошибка доступа |
| Записать критерии | Причина, чужой шум, неполнота, альтернативы | Можно отклонить убедительный неверный ответ |
| Сравнить | Ручное расследование и несколько запусков агента | Понятны польза, ошибки и стоимость проверки |

Данные продукта передавайте только через разрешённую вашей командой модель и контур. В публичные учебные материалы идут только синтетические данные. Не переносите demo kubeconfig и права доступа в production.

Для своего replay не подменяйте файлы уже используемого BUG-LAB-01: сделайте новый пакет с собственными ожиданиями. Учебный eval знает конкретный сюжет; его PASS нельзя использовать для другого бага без новой рубрики. Сначала сформулируйте проверку, затем подключайте агенту данные.

Полезный результат первого дня: один сохранённый кейс, один работающий источник, отчёт с доказательствами и список известных ограничений. Собственный Python runtime или новый фреймворк добавляйте под конкретную необходимость, а не как обязательный первый шаг.

## 8. Путь к CI и развёртыванию

В этом комплекте есть локальный runtime, MCP и проверки. Готового проверенного production-развёртывания агента и GitLab quality gate эта памятка не обещает. Следующие пункты — план отдельной интеграции:

- зафиксировать версии зависимостей, модель, входы и рубрику;
- вынести секреты в средства CI и ограничить доступ инструментов;
- задать таймауты, стоимость и поведение при недоступности модели;
- сохранять stdout, вызовы, verdict и ошибки проверки как артефакты;
- разделять «нарушен критерий», «не хватает доказательств» и «техническая ошибка»;
- сначала публиковать отчёт без блокировки релиза, затем согласовать условия quality gate.

Не блокируйте релиз только по свободному тексту модели или полю confidence. Поведенческий eval проверяет агента на выбранных сценариях; это не замена продуктовым тестам.
