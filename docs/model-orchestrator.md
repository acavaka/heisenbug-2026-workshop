# Модельный оркестратор QAI

Основной Python-режим теперь управляется моделью: она выбирает специалиста, формулирует вопрос, оценивает результат и решает, нужен ли досбор. Runtime не запускает analyzer/investigator/checker автоматически. Общие правила выбора — `workshop/prompts/rules-orchestration.md`, включённые в промпт orchestrator и адаптеры редакторов.

## Запуск

Из корня проекта, с подготовленными venv и доступом к модели:

```bash
python workshop/e2e.py --read-only BUG-1024
python workshop/e2e.py --read-only --mode workflow BUG-1024
```

Первая команда — новый основной режим. Вторая — прежний фиксированный baseline для сравнения, включая его однократный автоматический инфраструктурный досбор. Не запускайте их на чужом стенде без разрешения. Для infrastructure нужны подготовленный QAI_MCP_CONFIG и соответствующая карточка; для BUG-LAB-01 сохраняется отдельный учебный runner из карточки trace_to_logs.

## Управляющие инструменты Python

| Инструмент | Что делает |
|---|---|
| `qai_delegate(role, question)` | Вызывает analyzer, investigator или checker по конкретному вопросу |
| `qai_state()` | Возвращает накопленные отчёты, первичные наблюдения или инфраструктурный каталог, остатки бюджета |
| `qai_set_type(investigation_type, reason)` | Явно выбирает/пересматривает application или infrastructure |
| `qai_submit(draft)` | Проверяет проект вердикта прежним валидатором; принятие завершает цикл |

Это функции текущего runtime, а не новые команды `qai_tool.py` и не новые MCP endpoints. Инструменты специалиста по-прежнему ограничены его ролью. Сам оркестратор не получает kubectl/read_file и другие средства сбора.

Начальный тип application — рабочее значение. Analyzer может предложить infrastructure; модель должна явно подтвердить его через qai_set_type, чтобы checker получил инструменты каталога вместо инструментов исходников. Тип нельзя молча изменить внутри draft. Переклассификация не меняет существующие ограничения MCP/источников и не включает CLI fallback.

Управляющие вызовы Python отправляются с `parallel_tool_calls=false`: после каждого действия модель получает результат и заново выбирает следующее. Это исключает заранее выданный пакет «собрать → проверить → вынести вердикт»; порядок ролей кодом не задаётся. Обычные инструменты специалистов сохраняют прежнее поведение.

К каждому делегированию runtime добавляет BUG-ID, результаты предыдущих ролей и реальные наблюдения. Для infrastructure источником ссылок служит общий EvidenceSession. Оркестратор может повторно вызвать investigator после checker или завершиться без всех трёх ролей, если обоснованно воздерживается. Пропуск роли не отменяет требований доказательств для high.

## Доказательства и завершение

Управляющие tool calls видны в трассе, но их пересказы не входят в первичные доказательства. `qai_delegate` не превращает текст роли в ответ kubectl. Application получает observations из исполнения инструментов; модель не вправе передавать tool_observations. Infrastructure использует прежний контракт refs и прежнюю проверку spec/Warning/UID.

Для `qai_submit` Python публикует полную схему draft с `strict: true`. Схема соответствует текущему типу расследования и обновляется после явного `qai_set_type` и получения новых наблюдений. Для infrastructure разрешённые значения ссылок берутся из текущего каталога: evidence ID и resource ID различаются, observation ID не подходит. При пустом каталоге допустимы только пустые списки соответствующих ссылок. Тип, ссылки и причину по-прежнему выбирает модель; runtime не дописывает поля и не подставляет доказательства. Строгая форма устраняет пропуски ключей, но не доказывает правильность выбранных ссылок или диагноза. При отсутствии `draft.investigation_type` ошибка прямо указывает на пропущенное поле, а не предлагает повторно менять уже выбранное направление.

OpenAI-совместимый провайдер должен поддерживать strict function calling; автоматического перехода на нестрогий режим нет. При отказе API результат остаётся техническим отказом. В редакторах тот же полный шаблон и правила исправления применяются инструкцией, а фактическая проверка инфраструктурного отчёта — через MCP `qai_validate`; формат API Python не гарантирует такое же поведение каждого редактора.

Принятый verdict фиксируется runtime и возвращается без повторного переписывания моделью. После принятия прекращаются даже оставшиеся tool calls из того же ответа модели. Свободный финальный текст без принятого submit, исчерпание шагов или ошибка модели дают технический отказ с validation_errors, а не успешный low. Обоснованный low, прошедший submit, остаётся нормальным результатом. e2e сохраняет эти различия через существующую проверку exit code.

По умолчанию максимум 8 делегирований (`QAI_MAX_DELEGATIONS`, 1–32), 16 шагов оркестратора, 2 отправки draft. У специалистов свои лимиты шагов/таймауты. Это конечный бюджет действий, а не общий wall-clock deadline; retries API могут занять заметное время. Отчёты и JSON могут быть крупными: управление размером контекста остаётся отдельным ограничением.

## Python и редакторы

В Python управляющие функции исполняются кодом. В Claude Code основная сессия выбирает субагентов; в Codex/Cursor используются доступные механизмы делегирования, а при их отсутствии — выполнение выбранной роли основной сессией. Не следует имитировать несуществующий отдельный процесс.

Общий протокол решения одинаков: конкретный вопрос → специалист → наблюдения/пробел → следующий выбор → проверка результата. Численные ограничения в редакторах задаются инструкцией, а не отдельным runtime-счётчиком.

Для infrastructure в редакторе вместо qai_submit используется настоящий MCP qai_validate. Все роли должны работать с одним investigation_id одного gateway. Если субагенты имеют изолированные MCP-процессы, роли выполняются основной сессией; ссылки между процессами не переносятся. Для application используется отдельный [application MCP](application-mcp.md) с тем же валидатором; все первичные наблюдения должны пройти через его qai_observe.

Явный вызов скилла/роли пользователем остаётся допустимым, но не даёт права обходить read-only и validator. Отредактированные prompts обновляются командой `python workshop/render.py`; новую инструкцию проверять в свежей сессии.

## Что смотреть в отчёте

`orchestration` содержит режим, статус accepted/rejected, фактические делегирования (роль, вопрос, завершение/ошибка), изменения типа и число submissions. `validation_attempts` сохраняет отвергнутые drafts. `tool_observations` содержит первичные результаты; JSONL trace дополнительно показывает управляющие вызовы.

Наличие блока orchestration не доказывает, что выбран лучший маршрут. Его нужно сравнивать с исходными данными, корректностью диагноза, временем и стоимостью. Старый workflow оставлен для такого сравнения, не как автоматический fallback нового агента.

## Проверка реализации

Приватный регрессионный набор ведущего проверяет разные траектории вместо единственного порядка: повторный investigator, checker до investigator, воздержание без обязательного обхода ролей, отказ поддельному high, коррекция, остановка после принятия, лимит делегирований и submissions, явный выбор типа, ошибка специалиста.

Интеграционная проверка использует реальный локальный stdio MCP с синтетическим replay и подставной LLM: Pod и события собираются разными делегированиями по решению оркестратора. Вердикт проходит неизменённый валидатор. Это проверка управления и транспорта, не измерение качества реальной модели. Live-стенд, Boutique и order-worker этим этапом не менялись.

## Проверка с настоящей моделью

Протоколы проверок и эталонные результаты хранятся у ведущего. Референсный API-профиль в `.env.example` — `gpt-4.1` для всех ролей. Для воспроизведения профиль задаётся `workshop/replay.py --model gpt-4.1`. Поддержка strict и качество расследования других моделей/провайдеров требуют отдельной проверки; успешный формат не означает правильный диагноз.

## Application: ссылки вместо ручного переписывания цитат

После replay BUG-LAB-01 модельный Python-режим принимает evidence с `evidence_ref` из
`application_catalog`. `harness/application_evidence.py` регистрирует точные строки успешных
инструментов; не использует отчёты ролей. Каталог также содержит observed_file_lines для
реально выданных строк read_file/code_search. ID относятся к одному Investigation.

Модель выбирает claim, kind, ссылку, виновный файл, причину и confidence. Runtime раскрывает
ссылку в source/quote, добавляет исполненные observations и запускает неизменённый
application-валидатор. Пустая ссылка допустима только для вывода/гипотезы без цитаты, не факта.
Неизвестные и чужие ссылки отклоняются. Формат сохранённого вердикта остаётся прежним.
Внутренний Python API сохраняет совместимость с полными draft source/quote; модельному tool
рекламируется только контракт ссылок. Baseline workflow использует полный формат. В редакторах обязателен [application MCP](application-mcp.md), использующий тот же reference compiler и полный валидатор.

Replay backend сообщает execution_context/collection_gaps и причину блокировки checker до
корреляции. Runtime не читает за модель источники. Свободный финальный текст не заменяет
qai_submit; после двух отклонённых отправок цикл прекращается без дополнительных LLM-вызовов.
Сравнивайте свои результаты по источникам; эталонные ответы ведущий выдаёт после попытки.
