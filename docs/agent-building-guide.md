# Первый агент для задач QA

После воркшопа начните с одного кейса своего проекта. Kubernetes, команда из четырёх ролей и собственный Python-харнесс не обязательны для первого полезного результата.

[Начало занятия](workshop-kit.md) · [Повторить учебный кейс](monday-replay-guide.md) · [Устройство QAI](model-orchestrator.md)

## Что мы собираем на занятии

В комплекте уже есть стенд, базовые роли, инструменты доступа и валидатор. Участник проверяет расследование, меняет инструкцию, подключает k8sgpt через MCP и реализует `trace_to_logs`. Мы расширяем подготовленного агента расследования дефектов. Пример разбора требований и минимальный цикл объясняют, как перенести подход на другие задачи; полноценную платформу с нуля за два часа мы не разрабатываем.

## Как выбрать подход

| Ситуация | С чего начать | Что проверять |
|---|---|---|
| Весь контекст уже есть, нужен черновик проверок | Один вызов модели с ясным форматом | Не выдуманы ли требования, покрыты ли границы |
| Шаги и ветвления известны заранее | Workflow с заданным порядком | Ошибки каждого шага, повторяемость и остановка |
| Следующий источник зависит от наблюдения | Один агент с инструментами | Выбор вызовов, аргументы, ограничения и ответ |
| Разделение контекста и доступа приносит пользу | Оркестратор со специализированными ролями | Потеря данных между ролями, лишние вызовы, качество проверки |

Начните с простейшего подхода, который проходит ваши проверки. Количество ролей само по себе не делает ответ качественнее. Дополнительная роль требует контекста, времени и проверки передачи данных.

## Из каких частей состоит агент

- **Модель** предлагает следующий шаг или ответ.
- **Контекст** содержит задачу, инструкции и наблюдения.
- **Инструменты** исполняют разрешённые действия и возвращают структурированный результат.
- **Harness / runtime** организует цикл, исполняет вызовы, управляет доступом и остановкой, сохраняет историю.
- **Проверки** отделяют допустимый результат от красивого, но необоснованного ответа.

Учебный псевдокод, а не готовая библиотека или команда запуска:

```python
context = [task, instructions]
for step in range(6):
    action = model(context, tools=[read_test_log])
    if action.final:
        return check_answer(action.answer)
    result = execute_allowed_tool(action.name, action.args)
    context += [action, result]
return needs_more_evidence(context)
```

В рабочем коде дополнительно нужны проверка аргументов, ограничения времени и объёма данных, обработка ошибок, безопасный доступ, журнал вызовов и понятная причина остановки. Готовый клиент уже реализует значительную часть этого. В Python-харнессе QAI модель выбирает делегирование, runtime исполняет его и проверяет вердикт. Редакторы используют свой цикл и общий валидатор через MCP. Изоляция ролей и бюджеты зависят от конкретного хоста; одинаковые инструкции не обеспечивают одинаковое поведение автоматически.

## Роль, Skill, tool и MCP

**Роль** — ответственность и доступ, например сбор данных без диагноза. **Agent Skill** — инструкция в `SKILL.md` с описанием, когда её применять; дополнительные скрипты, справочники и шаблоны кладут рядом по необходимости. **Tool** — исполняемая функция с контрактом входа и выхода. **MCP** — протокол подключения инструментов и источников к клиенту, а не модель и не валидатор смысла.

В QAI каталог `workshop/skills/` исторически содержит Python-инструменты. Задание `trace_to_logs` создаёт инструмент и его описание; это не полный пакет Agent Skill. `/qai` — инструкция входа в расследование. Источник общих инструкций — `workshop/prompts/`, адаптеры генерирует `python workshop/render.py`.

Минимальный пакет навыка для своего проекта:

```text
triage-test-failure/
  SKILL.md       # когда применять, входы, действия, результат и остановка
  references/    # только нужные правила предметной области
  scripts/       # при необходимости, один проверяемый способ получить данные
  assets/        # при необходимости, шаблон результата
```

Не заполняйте каталоги ради структуры. Важнее проверить, что агент выбирает навык в нужной ситуации, следует инструкции и корректно останавливается при отсутствии данных. Для инструмента используйте [контракт и шаблон](tool-authoring.md).

## Пример для тестирования требований

Синтетическое требование: «Повторный запрос на создание заявки не создаёт дубликат».

| Раздел ответа | Пример |
|---|---|
| Подтверждённое ожидание | Повтор не создаёт вторую заявку |
| Вопрос к команде | Что определяет повтор: ключ, содержание или пользователь? |
| Вопрос к команде | Каков срок действия защиты и какой ответ возвращается? |
| Проверки-кандидаты | Последовательный и конкурентный повтор, новая заявка |
| Зависимость проверки | Ожидание для повтора через сутки уточняется после ответа о сроке |

Модель не должна подменять отсутствующие требования собственными решениями. Сначала согласуйте ожидания, затем превращайте их в тесты. Этот пример не содержит решения учебных багов.

## Чек-лист первого пилота

1. Выберите один вопрос, который регулярно отнимает время. Запишите полезный результат и кто его принимает.
2. Получите разрешённые обезличенные данные. Начните с файлов или одного read-only API.
3. Возьмите привычный клиент. Добавьте короткую инструкцию и один инструмент с явными входами, выходами и ошибками.
4. Подготовьте небольшой начальный набор случаев: успешный, недостаточные данные, посторонний сигнал и варианты своего проекта. Пять случаев — удобный старт, а не статистическое доказательство качества.
5. Сохраните ручное решение и результаты агента. Оцените верность, пропуски, необоснованную уверенность, время и затраты. Повторите прогоны, чтобы увидеть нестабильность.
6. Меняйте по одному элементу. Сохраняйте первую неудачную попытку и сравнивайте одинаковые входы.
7. Только после полезного результата решайте, нужны ли отдельные роли, свой runtime, framework и CI. Сначала публикуйте отчёт, затем обсуждайте блокирующий quality gate.

`valid=true` проверяет установленный контракт и происхождение ссылок, но не доказывает корректность любой интерпретации. Поведенческие ключи учебных кейсов остаются у ведущего. Для своего пилота создайте собственные критерии на разрешённых данных.

## Готовый клиент, framework или свой harness

| Вариант | Когда полезен | Что остаётся вашей работой |
|---|---|---|
| Codex, Cursor, Claude Code, Hermes | Быстро проверить кейс в существующем агенте | Инструкция, интеграция, доступ и оценка результата |
| Framework, например LangGraph | Нужно программно управлять состоянием и выполнением | Собрать приложение, инструменты, хранение и проверки |
| Свой компактный harness | Требуются конкретные ограничения, трассировка или учебная прозрачность | Поддерживать весь цикл и его сбои |

Hermes — отдельная среда исполнения. Его provider `openai-codex` поддерживает вход через ChatGPT/Codex subscription. Отдельный optional runtime `codex_app_server` передаёт выполнение цикла Codex. Это разные режимы. Доступные модели и лимиты зависят от учётной записи. Установка локального клиента не означает локальный запуск модели или работу без интернета. Hermes — демонстрация ведущего, он не нужен для четырёх обязательных заданий.
