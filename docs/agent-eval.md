# Зачем нужен eval агента

Unit-тест проверяет работу функции или ограничения runtime. Валидатор проверяет структуру
вердикта и происхождение цитат. Поведенческий eval сравнивает расследование с ожидаемым
поведением на контролируемом случае. Человек проверяет причинное объяснение и его границы.

Ключи ответов и тесты с готовыми диагнозами учебных кейсов хранятся у ведущего отдельно.
Публичный репозиторий содержит обычный строгий валидатор, тесты механизмов и проверки
контракта trace_to_logs. Они не подставляют участнику готовую реализацию или итог расследования.

```bash
# Только публичные unit tests, без модели и стенда:
workshop/.venv/bin/python -m unittest discover -s tests/workshop -v
# Проверка своей correlate; до реализации ожидается FAIL:
python workshop/exercises/trace_to_logs/run.py check
```

Python application runner сохраняет validation.json: contract_valid, contract_errors
и behavioral_eval.status=not_run. Успешный exit подтверждает принятие контракта, а не
прохождение приватной поведенческой оценки. В MCP нужен фактический valid=true.
Не выдавайте отсутствие приватной проверки за её PASS. Технический отказ отличается
от принятого low с ограничениями и конкретным запросом недостающих данных.

Для своего проекта заведите отдельный evaluation-набор, недоступный исследующему агенту:
известная причина, недостаточные данные, ложный след, недоступный источник. Ожидания
включают положительные и отрицательные критерии: какие выводы обоснованы и что нельзя
утверждать. Сохраняйте входы, реальные вызовы инструментов, версию промптов и результат.
После изменения модели, описания инструмента или runtime повторяйте затронутые случаи.
Несколько удачных ответов не доказывают надёжность на любых задачах.
