# Контракт доказательств: application и infrastructure

Модель выбирает наблюдения и объясняет причинную связь. Runtime хранит исходные ответы, точные
цитаты и происхождение; раскрывает ссылки и вызывает существующий `validate_verdict`.
`harness/evidence.py` общий для Python и MCP gateway. Валидаторы `verdict.py` и `infra_verdict.py`
проверяют раскрытые наблюдения. Код не повышает confidence и не достраивает отсутствующие факты.

## Python

Запуск остаётся прежним: `python workshop/e2e.py --read-only BUG-INFRA-LIVE-01`,
с `QAI_MCP_CONFIG` на локальный live-профиль. Данные из фактических MCP-вызовов investigator
попадают в каталог текущего trace. Checker и orchestrator получают каталог; `qai_evidence_get`
по умолчанию возвращает выбранный фрагмент; full_observation=true позволяет прочитать исходный ответ целиком. JSON этого инструмента не обрезается на границе 8000 символов.

Сохранённый отчёт содержит раскрытые `evidence`, `culprit_resources`, реальные `tool_observations`,
`evidence_catalog` и исходные ссылки. Отвергнутые ответы сохраняются в `validation_attempts`.
Доступна одна попытка исправления; окончательная ошибка возвращает low с validation_errors.
Такой low — технический отказ проверки, а не успешно проверенный диагноз с низкой уверенностью.

## MCP в Claude Code, Codex, Cursor

Настройки подключения остаются прежними: `workshop/mcp_gateway.py --config <upstream config>`.
После обновления переподключите MCP. Gateway объявляет пять k8sgpt tools и пять QAI tools.
Префикс имени зависит от хоста, например `mcp__k8sgpt__qai_begin`.

1. Оркестратор: `qai_begin({"bug_id":"BUG-INFRA-LIVE-01"})`. Сохранить выданный `investigation_id`.
2. Investigator: `qai_observe` с тем же ID, `tool` и `arguments` по обнаруженной схеме k8sgpt.
   Пример аргументов: `{"investigation_id":"<ID>","tool":"list-resources","arguments":{"namespace":"qai-training","resourceType":"pods","labelSelector":"app=checkout-probe"}}`.
3. Из ответа взять фактическое имя Pod; получить `get-resource` и `list-events` через `qai_observe`.
   Namespace обязателен. В list-events использовать имя Pod, а не Deployment.
4. Checker: `qai_catalog({"investigation_id":"<ID>"})`; при необходимости
   `qai_evidence_get({"investigation_id":"<ID>","evidence_id":"<ID>:E1"})`.
   По умолчанию возвращается фрагмент и метаданные; для полного ответа добавьте full_observation=true.
   Один Pod даёт несколько ссылок — не загружайте его полный ответ повторно для каждой ссылки.
5. Оркестратор: подготовить draft и вызвать `qai_validate({"investigation_id":"<ID>","draft":{...}})`.
   Только `valid:true` означает принятие. Показывать возвращённый полный `verdict`, не переписывать его вручную.
   При `valid:false` verdict=null, errors объясняет отказ; можно исправить draft, сохраняя реальный confidence.

Один investigation_id передаётся всем ролям. Gateway хранит сессии в памяти (до 32 расследований,
до 256 наблюдений на расследование); после перезапуска нужно заново собрать данные. Он не читает
файлы отчётов и не принимает импорт наблюдений. Разные процессы gateway не делят сессии:
если хост изолирует MCP по субагентам, выполняйте роли последовательно в основной сессии.
Raw get-resource/list-events остаются совместимыми диагностическими вызовами, но вне qai_observe
не регистрируют доказательства. Нельзя выдать их пересказ за проверенный каталог.

Ограничения namespace, allowed tools, explain=false и read-only RBAC остаются прежними.
QAI-инструменты не предоставляют новых операций Kubernetes. `qai_validate` не использует ключ LLM:
в редакторах модель предоставляется самим хостом, а Python e2e использует настроенный API.

## Ответ модели и полный отчёт

Модель заполняет обычные смысловые поля: bug_id, investigation_type=infrastructure, root_cause,
culprit_files=[], confidence, reasons, false_leads, red_team (три ответа), limitations, fix_direction.
Вместо полных ссылок на источник:

```json
{
  "culprit_resource_refs": ["<investigation_id>:R1"],
  "evidence": [
    {"claim":"Наблюдаемая конфигурация требует зависимость", "kind":"ФАКТ", "evidence_refs":["<investigation_id>:E1"]},
    {"claim":"Связанное событие сообщает об ошибке зависимости", "kind":"ФАКТ", "evidence_refs":["<investigation_id>:E3"]}
  ]
}
```

Это фрагмент, не полный draft. ID берутся из каталога, числа E1/E3 не фиксированы.
Runtime не принимает от модели source/quote/resource/evidence_role, culprit_resources или
сырой tool_observations. Для ВЫВОД/ГИПОТЕЗА тоже нужны ссылки, но такие записи не становятся
ФАКТами автоматически и не заменяют обязательные факты для high.

Каталог хранит spec как configuration, status как context и точное значение message
Warning-события как symptom, с временными полями события. Цитаты извлекаются из оригинальных
JSON-диапазонов: не склеиваются, не пересериализуются, не переносятся между прогонами.
Если полная spec содержит Go HTML escapes (например \u003e), которые существующий валидатор
не сопоставляет с декодированным JSON, extractor спускается к вложенным исходным фрагментам.
Непринимаемые фрагменты отмечаются в uncitable_paths, не переписываются. Это форматное
ограничение цитирования, а не недоступность источника; весь исходный ответ остаётся доступен.
Ошибки/пустые ответы остаются видны как доступность источника, но не дают обязательного доказательства.
Успешные ответы MCP без специального extractor (например текст логов или analyze) получают
context-ссылку на оригинальный ответ. Их можно цитировать; они не заменяют configuration/symptom.

`collection_gaps` перечисляет недособранные источники с именем инструмента и аргументами.
Это общий checklist Python и MCP: запросить spec/status/UID и события нужного объекта,
а для running-контейнера — текущие логи. Логи `previous=true` не закрывают чтение текущего
контейнера. Успешная пустая выборка событий закрывает запрос; Warning ради завершения не нужен.
Checklist не содержит диагноза и не меняет confidence. При недоступном источнике допускается
один досбор, затем агент указывает limitation; ждать пустого списка бесконечно нельзя.
Непринимаемые Warning message с Go escapes остаются context с uncitable_paths; high по ним
не разрешается. При отказе high selection_help показывает доступные и выбранные ссылки по
ролям. Это подсказка выбора, а не автоматическое добавление фактов или повышение confidence.

High требует configuration + symptom для каждого выбранного kind/namespace/name/UID.
Пустые events, Normal events, общий analyze или только Ready=True этого условия не выполняют.
Проверка устанавливает структуру/происхождение, не причинность, полноту или актуальность события.
Агент и участник по-прежнему проверяют интервал инцидента, альтернативы и механизм отказа.

ID вызова хранится в `observations[].observation_id`. Он служебный: в `evidence_refs` и
`qai_evidence_get` принимаются только `evidence[].id`, а виновники выбираются из `resources[].id`.
Пустые выборки и ошибки вызовов остаются в observations для описания limitations, но не создают
цитируемых доказательств. Python не предлагает reader при пустом evidence; в редакторе агент
должен проверить каталог перед вызовом reader. Подробности диагностики и её отдельного eval —
в `docs/agent-eval.md`: наличие корректной ссылки ещё не означает, что причина доказана.

## Application и новые источники

Application в модельном Python-режиме и редакторах использует собственный runtime-каталог.
Модель передаёт evidence[{claim, kind, evidence_ref}] с одиночной ссылкой и culprit_files
из observed_file_lines. Runtime раскрывает source/quote и вызывает прежний application-валидатор.
Фиксированный workflow сохраняет полный формат source/quote. Подключение и точный draft —
[application MCP](application-mcp.md). Каталоги application/infrastructure не смешиваются.

В файловом BUG-LAB-01 корреляция trace_to_logs открывает доступ checker к коду;
успешная корреляция не доказывает root cause сама по себе. Для no-ids и invalid-trace
runtime возвращает необходимость досбора. Новые источники требуют адаптеров,
проверок статуса/полноты и отрицательных примеров, а не одного добавления поля evidence_ref.

## Проверки

В публичном комплекте есть проверки транспорта и контракта инструмента. Расширенные проверки
с эталонными вердиктами хранятся отдельно у ведущего. В собственном расследовании проверяйте
фактический ответ `qai_validate`, цитаты, принадлежность источников и ограничения.
Эти проверки не заменяют оценку причинного вывода или проверку UI выбранного редактора.
