# 2. Сделайте ответ агента удобнее для проверки

**12 минут.** Добавьте в инструкцию сборщика данных требование явно проверять утверждения из обращения. Сравните ответ до изменения и после него на одинаковом примере.

Вы научитесь превращать пожелание «отвечай лучше» в конкретное требование. Первый ответ уже может быть правильным: наша цель — увидеть, стало ли проще найти источник и границу вывода.

## Что меняем

Только [инструкцию investigator](../../prompts/qai-data-investigator.md): `workshop/prompts/qai-data-investigator.md`. Затем генератор обновит её копии для редакторов. Проверки, данные и правила доступа остаются прежними.

Все команды выполняйте из корня проекта — папки с `workshop/` и `fixtures/`.
Используйте подготовленное Python-окружение. В macOS/Linux:

```bash
source workshop/.venv/bin/activate
```

В Windows PowerShell:

```powershell
workshop/.venv/Scripts/Activate.ps1
```

## Шаг 1. Получите ответ до изменения — 3 минуты

В Codex, Claude Code или Cursor откройте новый чат и вставьте этот запрос. Сохраните ответ в `workshop/.local/exercise-02-before.md`.

```text
Проверь роль qai-data-investigator на файловом synthetic replay, без доступа к стенду.
Прочитай workshop/prompts/qai-data-investigator.md и оба включаемых файла
workshop/prompts/rules-infrastructure.md и workshop/prompts/rules-evidence.md.
Репорт: fixtures/tracker/BUG-INFRA-01.md.
Входные наблюдения: fixtures/behavioral/infra-startup/healthy.json.
Используй только эти входные файлы как данные; не читай known-bad, подсказки и ответы ведущего.
Выдай отчёт investigator по инструкции. Источник помечай как replay-файл с JSON-путём,
не изображай вызовы инструментов, которых не было. Не редактируй файлы.

```

Дождитесь окончания ответа. Если ожидание превышает две минуты, позовите ведущего. Перед изменением инструкции завершите или остановите первый запуск и отметьте, если он не завершился.

## Шаг 2. Измените инструкцию — 3 минуты

Добавьте раздел «Проверка утверждений репорта». Для каждого существенного утверждения нужны: наблюдение с источником, статус проверки и граница знания.

Можно написать раздел самостоятельно или вставить в рабочий чат:

```text
Внеси одну правку в workshop/prompts/qai-data-investigator.md.
Добавь раздел формата ответа «Проверка утверждений репорта».
Для каждого существенного утверждения потребуй:
1. Что утверждал репорт.
2. Какое наблюдение с источником подтверждает или опровергает утверждение.
3. Статус: подтверждено / противоречит текущим данным / неизвестно.
4. Границу знания по времени и следующий запрос при недостатке данных.
Сохрани существующие правила. Не добавляй конкретные BUG-ID, имена Pod или диагнозы.
Не меняй другие исходники, данные, валидаторы, правила доступа и confidence-политику.
Не читай решения и материалы ведущего. Покажи diff. Генерацию я выполню отдельно.
```

В терминале выполните:

```bash
python workshop/render.py
python workshop/render.py --check
git diff -- workshop/prompts/qai-data-investigator.md
```

Проверьте свою правку. Если в diff есть прежние изменения, не сбрасывайте их. Сгенерированные копии вручную редактировать не нужно.

## Шаг 3. Получите ответ после изменения — 3 минуты

Откройте ещё один новый чат с той же моделью. Вставьте **тот же запрос из шага 1**. Сохраните ответ в `workshop/.local/exercise-02-after.md`.

Не вставляйте первый ответ в новый чат и не подсказывайте ожидаемый диагноз. Сравниваем работу инструкции на одинаковых входных данных.

## Шаг 4. Сравните — 3 минуты

Создайте `workshop/.local/exercise-02.md`: редактор и модель, текст правки, пути к двум ответам и один конкретный пример до/после.

Ответьте: легче ли теперь проверить утверждение? Видно ли, что известно сейчас, а что неизвестно о прошлом инциденте? Если требование не выполнено, запишите это как результат проверки.

## Если вы выбрали Python вместо редактора

До правки запустите:

```bash
python workshop/replay.py --cases healthy --output workshop/.local/exercise-02-before
```

После его завершения, правки и render:

```bash
python workshop/replay.py --cases healthy --output workshop/.local/exercise-02-after
```

Нужен заранее настроенный доступ к API модели. Данные синтетические, обращения к живому стенду нет. Отчёт investigator ищите в `healthy-1/console.log`, итог — в `healthy-1/BUG-INFRA-01.json`. `summary.json` проверяет контракт, а смысл вы сверяете по источникам. При отказе прочитайте `contract_errors` и `validation_errors`; сохранённый ответ не исправляйте. Для повторов выбирайте новые каталоги.

## Что должно получиться

Одна общая правка, успешный `render.py --check` и сравнение двух ответов с примером. «Уже было правильно, стало явнее» — хороший результат. Два запуска не доказывают устойчивого улучшения модели.

В редакторе это проверка одной роли: MCP и `qai_validate` здесь не нужны. Python запускает всю команду; результаты двух маршрутов не сравнивайте как бенчмарк.

Если модель недоступна, ведущий даст сохранённую пару ответов для обсуждения. Свою правку можно подготовить, но её эффект тогда остаётся непроверенным. На общей минуте 20 переходим дальше.
