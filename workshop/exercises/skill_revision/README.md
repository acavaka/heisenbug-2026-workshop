# 2. Улучшить общую инструкцию — 12 минут (8–20)

**Результат:** одна небольшая правка и проверка её эффекта на одинаковых входных данных.
В этом репозитории навыком расследования управляют общие инструкции ролей, а Python-инструменты
живут в `workshop/skills`. Здесь меняем инструкцию роли; новый инструмент напишем в четвёртом задании.

Текущие правила уже запрещают ошибку из задания 1. Не удаляйте их ради демонстрации ошибки.
Наша доработка — сделать сверку утверждений репорта с наблюдениями явно проверяемой в отчёте investigator.

## Задача

В [исходнике роли](../../prompts/qai-data-investigator.md) добавьте один раздел формата ответа:
**«Проверка утверждений репорта»**. Для существенного утверждения агент должен показать:

- что утверждал репорт;
- какое наблюдение с источником подтверждает или опровергает это утверждение;
- статус проверки: подтверждено / противоречит текущим данным / неизвестно;
- границу знания: текущее состояние или прошлый инцидент, какой запрос нужен дальше.

Не вставляйте ответ для конкретного BUG-ID и не меняйте валидатор, confidence-политику,
правила доступа или алгоритм инструментов. Формулировку можно написать с помощью агента.

## По минутам

| Минуты задания | Действие |
|---|---|
| 0–3 | Получить и сохранить baseline на healthy replay выбранным маршрутом ниже. |
| 3–6 | Добавить один блок в исходник роли; сгенерировать файлы для редакторов. |
| 6–9 | Повторить на тех же данных и модели в новой сессии/запуске. |
| 9–12 | Сравнить ответы и записать, что изменилось и чего сравнение не доказывает. |

Из корня репозитория, в заранее подготовленном Python-окружении:

```bash
python workshop/render.py
python workshop/render.py --check
```

Редактируем только исходник `workshop/prompts/qai-data-investigator.md`, не его сгенерированные
копии. Python читает исходник, редакторы получают обновление через render. Для повторного
запуска в редакторе откройте новую сессию и явно укажите прочитать обновлённые файлы.

## Как получить до/после

**Python-харнесс с заранее настроенным API:** baseline до правки, after после правки и render:

```bash
python workshop/replay.py --cases healthy --output workshop/.local/exercise-02-before
python workshop/replay.py --cases healthy --output workshop/.local/exercise-02-after
```

Выполняйте команды по отдельности в нужный момент. Дождитесь окончания before перед правкой. Они используют реальную LLM и изолированный
синтетический MCP; живой стенд не читается. Не меняйте модель между запусками.
Если каталог уже существует, выберите новые имена для ОБОИХ запусков; старые результаты не стирайте.
В каждом каталоге смотрите `healthy-1/console.log` (раздел `qai-data-investigator`),
`healthy-1/BUG-INFRA-01.json` и `summary.json`. Нужный новый раздел — в отчёте роли,
он не обязан появиться отдельным полем итогового JSON. `summary.json` проверяет контракт, но не правильность диагноза: её оцените сами по источникам.
Если `contract_valid=false`, прочитайте `contract_errors` и откройте `validation_errors` и `validation_attempts`
в отчёте: отделите ошибку JSON-контракта от ошибки диагноза. Не редактируйте сохранённый
ответ. После исправления запускайте в новом каталоге и сохраните исходный FAIL.

**Claude Code / Codex / Cursor:** два независимых новых диалога с одной моделью и одинаковым
запросом ниже: первый до правки, второй после render. Сохраните оба ответа в `.local`.
Это файловая проверка одной роли, не полный `/qai` и не проверка MCP редактора.
Здесь `qai_validate` не требуется: проверяем формат и доказательность отчёта роли, а не
итоговый вердикт. Авторизация редактора по подписке подходит; отдельный API-ключ не нужен.

```text
Проверь роль qai-data-investigator на файловом synthetic replay, без доступа к стенду.
Прочитай workshop/prompts/qai-data-investigator.md и оба включаемых файла
workshop/prompts/rules-infrastructure.md и workshop/prompts/rules-evidence.md.
Репорт: fixtures/tracker/BUG-INFRA-01.md.
Входные наблюдения: fixtures/behavioral/infra-startup/healthy.json.
Используй только эти входные файлы как данные; не читай known-bad, подсказки и ответы ведущего.
Выдай отчёт investigator по инструкции. Источник помечай как replay-файл с JSON-путём,
не изображай вызовы инструментов, которых не было. Не редактируй файлы.
```

В Python используется текущий модельный оркестратор: он выбирает роли и может запросить
досбор. Не требуйте одинакового порядка или количества вызовов до/после. Сравнивайте
один и тот же отчёт investigator и подтверждение его утверждений.

Не сравнивайте эти два маршрута как бенчмарк моделей: Python запускает всю команду,
редактор здесь проверяет инструкцию одной роли. Учебная цель и критерии сверки общие.

## Приёмка

Сохраните `workshop/.local/exercise-02.md`: хост/модель, входные файлы, текст изменения,
пути к двум ответам и по одному примеру из каждого.

- Правка общая, без имён кейса/Pod и без готового диагноза; `render.py --check` проходит.
- В новом отчёте проверка утверждения содержит источник, статус и границу знания.
- Running/Ready не превращены в доказательство исправности приложения; ERROR — в причину запуска.
- Сравнение честное: «уже было корректно, стало явнее» — допустимый результат.
  Два запуска не доказывают устойчивое улучшение модели. FAIL разобран, а не скрыт ослаблением проверки.

Если вызов модели занимает больше 2 минут, зовите ведущего. Перед правкой дождитесь
завершения baseline или остановите его (Ctrl+C) и отметьте как незавершённый. Не меняйте
инструкции во время baseline: Python читает их при запуске каждой роли. Затем переходите к правке;
сравните ответы в паре на работающем хосте. Без ответа after отмечайте «правка подготовлена,
эффект не проверен», а не «задание пройдено». Общая граница — минута 20 воркшопа.
